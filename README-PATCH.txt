PATCH v12 — إصلاح سقوط الموقع على صفحات الإدارة (المستخدمين/التقارير/الفروع/الدليل)
ne zam POS — 2026-10-06
════════════════════════════════════════════════════════════════════

■ اختبارك هو اللي حدد المشكلة بالظبط ■
تعبّت وتصفحت كل الصفحات ~100 مرة وما وقعت غير لما توصل لصفحات
الإدارة (المستخدمين، التقارير، الفروع) — وصفحة دليل المستخدم بتقع معاهم.
ده مش بس صح — ده كان مفتاح حل اللغز كله.

■ إيه اللي بيحصل بالظبط؟ ■

1) الصفحات نفسها بقت سريعة من v11 (كله بيرجع من الكاش "HIT" بـ 8-12
   ملي ثانية وبصفر مجهود CPU) — عشان كده 100 تصفح على الصفحات
   العادية عدّوا من غير أي مشكلة.

2) لكن صفحات الإدارة بتطلب بياناتها من APIs مش متخزنة على الحافة:
   /api/users، /api/branches، /api/reports/branches، /api/expenses
   كل طلب من دول بيفتح Prisma (قاعدة البيانات) من الأول.
   وأول مرة Prisma تشتغل جوا "isolate" جديد بتجهّز محرك WASM —
   ده بياكل أكتر من الـ 10ms CPU المسموح بيهم في الخطة المجانية
   → Error 1102 → الموقع كله بيقع ويرجع لوحده.
   (سجلات wrangler tail كانت موضحة إن أصغر API زي /api/branches
   بيقع بنفس الخطأ — دلوقتي عرفنا ليه).

3) صفحة دليل المستخدم ما ليهاش API أصلاً — كانت بتقع «معاهم» لأن
   مفيش نسخة سليمة منها في كاش المتصفح وقت الانهيار.

■ الحل في v12 ■

1) نفس الكاش المجرّب اللي شافه في الداشبورد/العملاء/المنتجات — اتضاف
   للـ APIs دي:
   • /api/branches          → كاش 60 ثانية (بتتغير نادراً)
   • /api/users             → كاش 30 ثانية
   • /api/reports/branches  → كاش 25 ثانية (نفس نهج التقارير)
   • /api/expenses          → كاش 20 ثانية (نفس نهج المنتجات)
   أي إضافة/تعديل/حذف (فرع أو مستخدم أو مصروف) بينزّل الكاش فوراً
   — فالبيانات بتفضل حية 100%. وأي بيعة جديدة بتنزّل كاش تقرير
   الفروع فوراً.

2) تحصين Service Worker (v6):
   • لو حصل خطأ 5xx وقت فتح أي صفحة → بيقدّم آخر نسخة سليمة من
     الكاش بدل صفحة الخطأ البيضا.
   • «صفحات طوارئ» بتتخزن أول ما يتثبت الـ SW: /pos، /dashboard،
     /products، /inventory، /customers، /users، /reports،
     /branches، /expenses، /guide، /login — كلها أغلفة ثابتة
     مفيهاش أي بيانات مستخدمين (اتأكدنا بنفسنا في فحص v11).
     يعني حتى لو الـ Worker وقع بالكامل، فتح صفحة دليل المستخدم
     أو المستخدمين هيجيب النسخة المخزنة بدل Error 1102.

3) تحصين خطوة النشر (علشان مشكلة الـ 503 اللي حصلت مع v11 متتكررش):
   • cf:build دلوقتي بينفّذ populate تلقائياً بعد كل بناء — مش ممكن
     تنساه زي المرة اللي فاتت.
   • السكربت بقى بيعدّ ملفات كاش الصفحات وبينبّهك لو أقل من 20
     (المفروض 36) قبل ما تعمل deploy.

■ ملفات الباتش (11 ملف) ■

  package.json                                  (cf:build شامل populate)
  scripts/populate-cache-assets.mjs             (فحص صحة الكاش)
  public/sw.js                                  (v6: طوارئ + 5xx fallback)
  src/lib/edgeCache.ts                          (مفاتيح مسح جديدة)
  src/app/api/branches/route.ts                 (كاش 60s + مسح)
  src/app/api/branches/[id]/route.ts            (مسح بعد تعديل/حذف)
  src/app/api/users/route.ts                    (كاش 30s + مسح)
  src/app/api/users/[id]/route.ts               (مسح بعد تعديل/حذف)
  src/app/api/reports/branches/route.ts         (كاش 25s)
  src/app/api/expenses/route.ts                 (كاش 20s + مسح)
  src/app/api/sales/route.ts                    (مسح كاش تقرير الفروع بعد البيع)

ملاحظة: open-next.config.ts بتاع v11 لازم يفضل زي ما هو (مش داخل
الباتش ده لأنك عندك خلاص).

■ خطوات التركيب ■

1) فك الضغط وانسخ الـ 11 ملف فوق نسختهم القديمة في D:\mobile-shop
   (حافظ على نفس هيكل المجلدات).

2) اتأكد إن مفيش سيرفر شغال، وبعدين:

       bun run cf:build

   هتشوف في الآخر:
       ✅ Populated static assets cache ...
          36 prerendered page cache files (APP_PAGE)

3) النشر:

       bun run cf:deploy

   (أو لو bun مش متاح: npm run cf:deploy — ولو Device Guard
   وقّف wrangler.exe فالأمر أصلاً بيستخدم node مباشر).

4) بعد النشر بقليلة: افتح الموقع، واعمل تحديث قوي (Ctrl+Shift+R)
   مرة واحدة علشان الـ Service Worker الجديد (v6) يتثبت.
   لو عايز تتأكد: DevTools → Application → Service Workers →
   المفروض تشوف shop-erp-v6.

■ اختبار بعد النشر ■

• افتح المستخدمين → التقارير → الفروع → الدليل → ورجع تاني، كررها
  كذا مرة متتالية وبسرعة. المفروض الكل يفتح فوري ومن غير ما الموقع يقع.
• لو حصل ضغط رهيبة جداً (مئات الطلبات في ثواني) ممكن يبطئ مؤقتاً —
  لكن مش هترجع لسيناريو «الموقع واقع وأصفار» لأن الـ SW بيقدّم
  آخر نسخة سليمة تلقائياً.

■ خطة الأمان النهائية (زي ما هي) ■

لو يوم ما وصلنا لحد الخطة المجانية، ترقية Workers المدفوعة ($5/شهر)
بترفع سقف الـ CPU من 10ms لـ 30 ثانية — أي ضغط مستحيل يقع الموقع.
القرار ليك، لكن v12 المفروض يحل مشكلتك الحالية بالكامل على المجاني.
